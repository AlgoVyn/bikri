## 1. Units and primitives

- Money: integer **paisa**. Quantity: integer **milli-units**. Rates: **basis points**.
- Use `BigInt` internally for any product that can exceed 2^53 (qty × price × bp); return `number`.
- `mulDivRound(a, b, c)`: exact `a × b ÷ c`, **round half away from zero**. Example: `mulDivRound(5, 1, 2) = 3`, `mulDivRound(-5, 1, 2) = -3`.
- `allocate(amount, weights)`: split an integer amount in proportion to integer weights, **largest-remainder method**: base share `floor(|amount| × wᵢ ÷ W)`; distribute the leftover paisa one each to the lines with the largest remainders; ties go to the lower line index; sign of `amount` is applied at the end. The shares always sum exactly to `amount`. If `W = 0`, all shares are 0.
- `roundTo(x, step)`: `mulDivRound(x, 1, step) × step` (step in paisa: 1, 100, 500, 1000).

## 2. Line totals

For each cart line:

```
gross    = mulDivRound(qty_milli, unit_price, 1000)
discount = 0                                   if no discount
         = min(discount_value, gross)          if type 'rs'   (value in paisa)
         = mulDivRound(gross, discount_value, 10000)  if type 'pct' (value in bp, max 10000)
net      = gross − discount
```

## 3. Bill totals

```
gross_total         = Σ gross
item_discount_total = Σ discount
subtotal            = Σ net
bill_discount       = min(value, subtotal)                     if 'rs'
                    = mulDivRound(subtotal, value, 10000)      if 'pct'
taxable             = subtotal − bill_discount
-- tax_mode 'exclusive' (default; prices are before tax):
tax                 = mulDivRound(taxable, tax_rate_bp, 10000)   (v1: shop rate)
pre_round           = taxable + tax
-- tax_mode 'inclusive' (prices are MRP including tax):
tax                 = taxable − mulDivRound(taxable, 10000, 10000 + tax_rate_bp)
pre_round           = taxable                                     (tax is inside the price, not added)
-- both:
total               = roundTo(pre_round, shop.round_total_to)     (default 100 = nearest rupee)
rounding            = total − pre_round                           (signed, |rounding| < round_total_to/2 + 1)
```

Tax is **off by default** (`shop.tax_rate_bp = 0`, `tax_mode = 'exclusive'`). The "Prices include tax" switch (`tax_mode = 'inclusive'`) is shown in Settings and the setup wizard **only when the tax rate is above 0**; with rate 0 both modes give `tax = 0` and identical totals. The mode is snapshotted on each sale as `sales.tax_inclusive`, so changing it affects new sales only.

Per-line allocations (stored on `sale_lines`, used for refunds and per-line profit):

```
bill_discount_alloc = allocate(bill_discount, nets)
tax_alloc           = allocate(tax, nets)
rounding_alloc      = allocate(rounding, nets)
exclusive:  line_final   = net − bill_discount_alloc + tax_alloc + rounding_alloc   (Σ line_final = total)
            line_revenue = net − bill_discount_alloc                              (excl. tax and rounding; used for profit)
inclusive:  line_final   = net − bill_discount_alloc + rounding_alloc             (Σ line_final = total)
            line_revenue = net − bill_discount_alloc − tax_alloc                  (ex-tax, so profit never includes tax)
```

Receipts and the cart show tax differently per mode: exclusive adds a `Sales tax 17%` row before the total; inclusive shows the total and then `Includes Sales tax 17%: Rs 1,700` ([06 §4.1](06-printing.md#41-sale-receipt-80-mm-48-columns)).

### 3.1 Discount limits

`discount_share_bp = mulDivRound(item_discount_total + bill_discount, 10000, gross_total)`. If it exceeds the current staff's `max_discount_bp`, payment requires a manager override ([05 §4.1](05-auth-and-roles.md#41-manager-override)); the sale writes `audit_log` `discount_over_limit`.

### 3.2 Below cost (REQ-B14)

A line is below cost when `line_revenue < mulDivRound(qty_milli, unit_cost, 1000)` where `unit_cost` = product `avg_cost` (or `last_cost` when `shop.cost_method = 'last'`). The cart shows "Below cost" on the line to everyone; completing the sale needs `sale.below_cost` or an override. `sale_lines.below_cost = 1`. Lines with unknown cost (0) are never below cost.

## 4. Payments

- Methods: `cash`, `card`, `bank_wallet` (JazzCash, Easypaisa, NayaPay, bank transfer), and **udhaar** (not a payment row; a ledger entry).
- Split (REQ-B08): the pay screen collects amounts per method; `Σ applied = total`. Udhaar part requires a customer.
- Cash: `cash_tendered ≥ cash_applied`; `change_given = cash_tendered − cash_applied`. Only the cash method can have change. Overpaying with card/bank-wallet is not allowed.
- Rows: one `payments` row per non-udhaar method with `amount = applied`. `sales.paid_total = Σ applied (non-udhaar)`, `sales.udhaar_amount = udhaar part`, `sales.cash_tendered`, `sales.change_given`.
- Quick cash chips: `Exact`, then `cashChips(due)` = the values `ceil(due / s) × s` for `s` in Rs 500, 1,000, 5,000, dropping any equal to `due` and duplicates, ascending (max 3). Vectors: Rs 1,450 → 1,500 · 2,000 · 5,000; Rs 40 → 500 · 1,000 · 5,000; Rs 4,300 → 4,500 · 5,000; Rs 5,000 → none (only Exact).

### 4.1 Credit limit

`balance_after = current_balance + udhaar_part`. If `credit_limit` is set and `balance_after > credit_limit`: show warning "Rs X over the limit of Rs Y" (amber). If `hard_limit = 1`, the Write-in-khata button is disabled unless a manager override is given.

## 5. Customer and supplier balances

- `balance = Σ ledger_entries.amount` for the party.
- Customer: sale on udhaar `+udhaar_part`; payment received `−amount`; refund `−refunds.udhaar_part` (§6.1); void of an udhaar bill `−udhaar_amount`; opening balance `+x`.
- Supplier: delivery `+total`; paid now `−paid_now`; pay supplier `−amount`; return to supplier `−total`, and `+refund_received` when the supplier pays money back (§10); opening `+x`.
- A negative customer balance means the customer is **in credit** (shown "In credit Rs X"); a negative supplier balance means an advance paid.
- `oldest_unpaid_at` (for the chase list): walk entries oldest-first, apply payments FIFO against debits; the earliest debit not fully covered gives the age.

## 6. Refunds

For a sale line with sold quantity `Q` (milli), final amount `F` (`line_final`), already refunded quantity `p`, refunding `q`:

```
line_refund = mulDivRound(F, p + q, Q) − mulDivRound(F, p, Q)
exact_amount = Σ line_refund
```

This guarantees that refunding every unit across any number of refunds returns exactly `F`.

### 6.1 Refunds on udhaar bills

Every refund is split automatically into a **paid part** (money handed back) and an **udhaar part** (reduces the customer's khata). The paid part comes first, capped at what the customer actually paid for this bill and has not had back yet:

```
remaining_paid   = sales.paid_total    − Σ refunds.amount      of earlier refunds of this sale
remaining_udhaar = sales.udhaar_amount − Σ refunds.udhaar_part of earlier refunds of this sale
udhaar_part      = min( max(exact_amount − max(remaining_paid, 0), 0), max(remaining_udhaar, 0) )
paid_exact       = exact_amount − udhaar_part
```

- `paid_exact = 0` (e.g. a fully udhaar bill, or everything paid has already been refunded): **no money is handed back**, `refunds.method = NULL`, `amount = 0`; the whole value reduces the khata. The refund dialog shows no method choice ("Rs 450 will be taken off Ali's khata").
- `paid_exact > 0`: method = `cash` by default, changeable to any method used on the original sale. Cash rounding below applies to `paid_exact` only.
- `udhaar_part > 0` writes `ledger_entries` (customer, `−udhaar_part`, source refund). If the customer has meanwhile paid the khata, their balance can go negative ("In credit Rs X", §5); that credit is used up by their next udhaar bill.
- A bill without an udhaar part (`udhaar_amount = 0`) never gets an udhaar part: `remaining_udhaar = 0`, so the formula puts everything in the paid part.

Rounding (REQ-B09) of the paid part, by `shop.refund_rounding` (default `nearest`), **only for method `cash`**:
- `nearest`: `amount = roundTo(paid_exact, 100)`; `down`: floor to rupee; `none`: exact.
- Cap: `amount ≤ remaining_paid`; if the rounded amount exceeds it, round down to the rupee instead.
- `rounding = amount − paid_exact` is stored on `refunds`; `amount = exact_amount − udhaar_part + rounding` (CHECK in [02](02-data-model.md#2-d1-schema-migration-0001_initsql)).
- Card / bank-wallet paid parts use `paid_exact` exactly.

## 7. Cost: weighted average

On each stock movement **with a unit cost** (`opening`, `purchase`, `received_godown`, `received_local`, `received_other`):

```
if on_hand_before ≤ 0:  avg_cost = unit_cost
else:                   avg_cost = mulDivRound(on_hand_before × avg_cost + qty × unit_cost, 1, on_hand_before + qty)
last_cost = unit_cost
```

Movements without unit cost (sales, refunds, damage, counts, returns) do not change `avg_cost`.

- The **server** is authoritative and computes **incrementally in server-apply order** (no history replay, which would not fit the Free plan's 10 ms CPU budget and would depend on device clocks): when it applies a costed movement it reads `on_hand_before = SELECT COALESCE(SUM(qty_delta_milli),0) FROM stock_movements WHERE product_id = ? AND id <> ?` (all movements already applied, any order) and the current `products.avg_cost`, applies the formula, and writes `products.avg_cost`, `last_cost` and `rev + 1` (+ `change_log`) in the same batch. Several costed movements for one product in one push are applied in op order.
- Tills compute the same provisionally from their local data so the UI is immediate, and take the server value on the next pull. Because order is server-apply order, a till and the server can differ by a few paisa until that pull; that is accepted.
- `on_hand_before ≤ 0` resets to the new unit cost (fixture C2).
- `shop.cost_method = 'last'` makes profit use `last_cost` instead (Dukaan behaviour). Default `avg`.
- Sales snapshot `unit_cost_snapshot` at sale time, so later deliveries never change past profit.

Supplier returns (`supplier_return`, §10) are outflows **without** a unit cost: they do not change `avg_cost`.

## 8. Day close

Scope: **one device (cash drawer)**, period = from the previous `day_closes.period_end` of this device (or device enrolment time) to now. All sums are `cash` only and filtered by `device_id` and `created_at` in `(period_start, period_end]`. The drawer uses **`created_at`** (when cash physically moved), while reports use **`business_date`**: a back-dated expense or delivery takes cash out of today's drawer but counts in the earlier day's profit. Each enrolled device is one drawer: never enrol two browsers that share one physical cash drawer.

```
opening_cash      = previous close's counted_cash (0 for the first close, editable "Opening float" only on the first close)
cash_sales        = Σ payments.amount   where direction='in',  method='cash', purpose='sale'
udhaar_cash_in    = Σ payments.amount   where direction='in',  method='cash', purpose='customer_payment'
pay_ins           = Σ cash_moves.amount where kind='pay_in'
supplier_cash_in  = Σ payments.amount   where direction='in',  method='cash', purpose='supplier_refund'
cash_refunds      = Σ payments.amount   where direction='out', method='cash', purpose IN ('refund','void')
cash_expenses     = Σ expenses.amount   where method='cash' and reverses_id IS NULL
                  − Σ expenses.amount   where method='cash' and reverses_id IS NOT NULL
supplier_cash_out = Σ payments.amount   where direction='out', method='cash', purpose IN ('supplier_payment','purchase_paid_now')
pay_outs          = Σ cash_moves.amount where kind='pay_out'

expected_cash = opening_cash + cash_sales + udhaar_cash_in + pay_ins + supplier_cash_in
              − cash_refunds − cash_expenses − supplier_cash_out − pay_outs
difference    = counted_cash − expected_cash      (0 → "Drawer is correct", < 0 → "Short", > 0 → "Over")
```

Note `cash_sales` uses the applied amount (tendered − change), so change handed back is never counted.

## 9. Reports formulas

For a date range [from, to] by `business_date` (and branch, v2):

| Figure | Formula |
|---|---|
| Sold (net sales) | Σ `sales.total` (status ≠ void) − Σ (`refunds.amount` + `refunds.udhaar_part`) in range |
| Bills | count of sales (status ≠ void) |
| Average bill | Sold ÷ Bills |
| Gross profit | Σ (`line_revenue` − qty × `unit_cost_snapshot`) for non-void sales − Σ refunded profit (§6) |
| Expenses | Σ `expenses.amount` (reversal rows, `reverses_id` set, count negative) |
| Net profit | Gross profit − Expenses |
| Profit margin | Gross profit ÷ Σ line_revenue |
| Udhaar given | Σ `sales.udhaar_amount` (non-void) − Σ `refunds.udhaar_part` |
| Udhaar received | Σ payments purpose `customer_payment` |
| Payment mix | Σ applied per method + udhaar, minus refunds per method (`amount` by `refunds.method`; `udhaar_part` from udhaar) |
| Tax collected | Σ `sales.tax` (non-void) − tax share of refunds (Σ `mulDivRound(tax_alloc, q, Q)` per refunded line, cumulative pattern) |
| Supplier returns | count, Σ `supplier_returns.total`, and the return difference Σ (`line_total` − `mulDivRound(qty_milli, cost_snapshot, 1000)`) — informational, **not** part of profit (like stock write-offs) |
| Best sellers | top 10 products by qty and by revenue (net of refunds) |
| Stock value | Σ over products with `track_stock = 1` of `mulDivRound(max(on_hand_milli, 0), avg_cost, 1000)` |

Refunds count on the date they happen, not on the original sale's date.

## 10. Return to supplier

Goods sent back to a supplier (faulty, wrong item, unsold stock) — screen in [screens/13](screens/13-suppliers-and-purchases.md#return-to-supplier), recipe in [02 §5](02-data-model.md#5-record-recipes-which-rows-each-action-writes).

```
unit_credit (default) = linked purchase_lines.landed_unit_cost     if the line is returned against a delivery line
                      = products.avg_cost                          otherwise (products.last_cost if avg_cost = 0)
line_total            = mulDivRound(qty_milli, unit_credit, 1000)
total                 = Σ line_total                                   → supplier ledger −total
cost_snapshot         = products.avg_cost at the time of the return
return_difference     = total − Σ mulDivRound(qty_milli, cost_snapshot, 1000)   (report only)
suggested_refund      = max(0, total − max(supplier_balance_before, 0))
```

- **Cost basis:** the supplier is credited at what that stock cost from them (the landed cost of the delivery line, so freight on their invoice comes back too), or at the current average cost when no delivery is linked. The user may edit `unit_credit` (e.g. the supplier accepts it back for less).
- **Average cost is unchanged:** the movement removes stock at the average (weighted-average inventory: taking units out at the average never changes the average). Any gap between the credit and the average is the `return_difference`, shown in Reports but not booked into profit.
- **Settlement:** the return always reduces what the shop owes (`ledger −total`). If that leaves the supplier owing the shop money (balance below 0) the dialog suggests `suggested_refund`; money received now is `refund_received` (0…total) by cash or bank/wallet, written as a `payments` row (in, `supplier_refund`) and `ledger +refund_received`. Cash received goes into this device's day close as `supplier_cash_in` (§8). Leaving it at 0 keeps an advance with the supplier ("Advance Rs 550"), settled by the next delivery.
- **Linked returns:** returned qty per delivery line ≤ received qty − already returned (UI limit; the server accepts more like any real event and records `sync_conflicts` `over_return`).
